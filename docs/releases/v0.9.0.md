# v0.9.0

Turkish version: [../../tr/docs/releases/v0.9.0.md](../../tr/docs/releases/v0.9.0.md)

Release tag: `v0.9.0`

CacheDB `0.9.0` is a stable, additive framework release that reduces
declarative repository wiring without moving correctness or capacity decisions
into runtime magic. It consolidates compile-time repository ergonomics, typed
route operations, and production evidence added after `0.8.0`.

## Main Changes

- The annotation processor infers a query predicate parameter only when a
  compatible method parameter has the same name. It also infers a single
  `WindowRequest`, unused integer limit, ID-compatible lookup parameter,
  `CacheWarmTarget`, and warm row limit when each role is unambiguous.
- Ambiguous declarations fail compilation. Parameter order and runtime
  reflection are not used as semantic contracts.
- Strict HOT and bounded SOURCE routes may return `CursorPage<T>` directly.
  Generated HOT code still proves fresh and complete coverage before returning
  a page.
- Cursor continuation preserves the original validated page limit.
  `CursorPage.map` preserves the opaque cursor and uses one pre-sized list.
- Every repository receives a generated `*CacheDbRoutes` companion containing
  immutable `RepositoryRouteRef` values. Warm plans, coverage checks, and test
  probes accept those typed references.
- A coverage scope must appear as exactly one `EQ` predicate against the same
  entity field in every query group.
- Actuator, startup logs, and Micrometer report HOT route count, projection and
  entity split, scoped routes, budgeted/unbudgeted routes, and the saturated
  sum of declared memory budgets. Route names are not metric tags.
- Explicit single-command durability helpers require a positive timeout before
  accepting a write. Bulk import remains on `CacheDurableBatchWriter` so
  batching and backpressure are preserved.
- PostgreSQL and SQL Server samples use direct cursor pages, inferred parameter
  roles, generated route references, and the immutable `0.9.0` package.

## Preserved Boundaries

- HOT routes read Redis only. A miss does not trigger hidden SQL I/O.
- SOURCE routes are explicit, bounded, indexed, keyset-paged, and time-limited
  SQL operations.
- Normal writes are accepted by Redis first; SQL durability remains
  asynchronous unless the caller explicitly uses a bounded durability wait.
- Repository implementations, codecs, route catalogs, and Spring adapters are
  generated at compile time without runtime reflection.
- Growing lists remain projection-first and keyset-paged. Offset pagination,
  generated controllers, automatic SQL fallback, and per-row durable bulk
  helpers were deliberately not added.

## Consumer Version

```xml
<properties>
    <cachedb.version>0.9.0</cachedb.version>
</properties>
```

Use exactly one provider starter:

```xml
<dependency>
    <groupId>com.reactor.cachedb</groupId>
    <artifactId>cachedb-spring-boot-starter-postgres</artifactId>
</dependency>
```

or:

```xml
<dependency>
    <groupId>com.reactor.cachedb</groupId>
    <artifactId>cachedb-spring-boot-starter-mssql</artifactId>
</dependency>
```

## Compatibility

The public API difference from `0.8.0` is additive. Existing explicit
annotation attributes, `HotWindow<T>`, and `SourceWindow<T>` signatures remain
valid. `CursorPage<T>` keeps the same `items` and `nextCursor` JSON shape.

Consumers should still compile and run their own provider integration tests.
The stricter coverage-scope validation can reveal a previously unsafe route at
compile time; that failure is a correctness gate, not a runtime regression.

## Distribution

- Maven packages: GitHub Packages under `com.reactor.cachedb`
- Release bundle: `cache-database-0.9.0-github-release.zip`
- Runnable examples: PostgreSQL and MSSQL sample repositories tagged `v0.9.0`

The release bundle contains binary, source, Javadoc, and POM artifacts for all
16 public modules, the BOM, documentation, and both sample projects.

## Validation

- Full Maven reactor: 318 tests, 0 failures, 0 errors, 12 existing conditional
  skips.
- PostgreSQL sample: Redis 8.2.1 and PostgreSQL 16 integration profile passed.
- SQL Server sample: Redis 8.2.1 and SQL Server 2022 integration profile passed.
- Public API compatibility, reflection-free framework principles, provider
  parity, declarative sample boundaries, documentation, Postman, artifact
  content, and whitespace gates passed.

Framework release evidence is not an application cutover certificate. Each
consumer still needs representative warm coverage, data parity, Redis memory
sizing, database/Redis HA evidence, canary limits, and rollback proof in its own
staging topology.
