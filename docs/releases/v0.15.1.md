# CacheDB 0.15.1

Turkish: [0.15.1 sürüm notları](../../tr/docs/releases/v0.15.1.md)

## Changes

- Connected schema bootstrap, DDL export, migration discovery/planning and SQL
  write-behind apply bounded JDBC column capabilities. Unknown/unsupported
  capabilities fall back to Oracle 1000, SQL Server 1024 or PostgreSQL 1600.
- Entity payloads, projection schemas, Redis index mutation and admin export
  accept at most 4096 fields. Payload-size, query and memory budgets remain.
- Wide mutable entities use chunked generated codecs/metamodels to respect the
  JVM method-size limit. Above 1000 fields, the processor reports a provider-limit
  note; above 4096, compilation fails. Oversized record constructors receive an
  explicit JVM-slot diagnostic.
- Physical-column checks include separate ID/version/deleted columns. Migration
  planning also counts existing unmapped columns. Oversized single-row parameter
  counts fail rather than being hidden by a batch size of one.
- Schema column inspection uses one bounded metadata result per table instead
  of one call per mapped column. Table/schema pattern wildcards are escaped.
- All three Java 21 samples align their BOM, processor, starters and doctor plugin
  at 0.15.1, with English/Turkish column-safety examples. Java 17 library bytecode
  and existing REST routes remain unchanged.

## Upgrade

1. Align every CacheDB dependency and annotation processor at 0.15.1. Recompile
   generated bindings; do not mix processor/core versions.
2. Upgrade all readers and workers before writing payloads above 1024 fields.
   Older 0.15.0 readers still enforce the old ceiling. Existing smaller payloads
   keep their format, null handling and duplicate-field behavior.
3. Validate the connected schema before admitting writes. The stricter checks
   intentionally reject definitions that fit the old generic ceiling but not
   the actual database. Count version and soft-delete columns too.
4. A 0.15.0 installation with the durable write fence already provisioned needs
   no additional business-table migration for this patch. Older unfenced workers
   still require the [durable write-fence migration](../durable-write-fences.md)
   and coordinated drain; retain version counters across upgrades.
5. Prefer narrow screen projections rather than using the higher ceiling as a
   reason to load an entire wide table for a list screen.

## Verification and Boundaries

Validation uses disposable EmaTech Kubernetes fixtures: the full reactor,
live PostgreSQL/SQL Server/Oracle column-boundary writes, six-node Redis Cluster
contracts, public API compatibility, packaged generated-codec latency, and three
sample provider-integration suites. Verified JARs are promoted without rebuilding.
Anonymous Maven consumption is checked after publication, independently from
source-reactor builds.

The 50 ms gate applies to correctness-checked generated-codec/snapshot scenarios,
including scenario first use but excluding JVM launch/compilation. It is not a
REST, SQL, WAN or production-capacity SLA. Legacy mapper functionality remains
covered by compatibility tests.

The live Oracle fixture advertises 1000 columns. Metadata/DDL tests exercise the
4096 capability path and a generated 4096-field class is compiled and round-tripped;
this does not certify a live Oracle extended installation. CacheDB never enables
`MAX_COLUMNS` automatically. Driver/database settings, row width, dropped column
slots and statement limits can impose tighter constraints.

Oracle service-name role transitions and SQL Server listener failover require
their separate coordinated topology. This framework package is not RAC/Data Guard,
Always On or application cutover certification.

See [database-aware column limits](../schema-column-limits.md) for examples.
The anonymous Maven repository remains
`https://esasmer-dou.github.io/cache-database/maven2`; GitHub Packages is an
additional authenticated channel, not a prerequisite for the samples.
