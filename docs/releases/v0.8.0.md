# v0.8.0

Turkish version: [../../tr/docs/releases/v0.8.0.md](../../tr/docs/releases/v0.8.0.md)

Release tag: `v0.8.0`

CacheDB `0.8.0` is a stable, additive framework release focused on explicit
route contracts, safer continuation, bounded background work, and lower-effort
application integration. It includes the additional framework UX engineering
cycles completed after `0.7.1`.

## Main Changes

- A continuation cursor is bound to its route, parent/filter scope, and sort
  contract. Reusing it on another route now fails explicitly.
- `CursorPage<T>` carries items and `nextCursor` through service and HTTP
  layers without exposing keyset internals to controllers.
- `@CacheRepositoryDefaults` centralizes hot population, page/window limits,
  memory budget, source-read limit, timeout, and warm limit at compile time.
- `CacheMemoryBudget` replaces unreadable raw byte literals in annotations.
- Repository capabilities, route population, generated route catalogs, and the
  Spring Boot route inventory make available operations inspectable without
  runtime reflection.
- Warm execution has typed targets, explicit dry-run/apply modes, invariant
  checked summaries, and one dry-run/apply/coverage test journey.
- Distributed jobs share a typed definition and bounded structured progress.
- `CacheDurableBatchWriter` owns batch flushing, receipt tracking, and bounded
  durability backpressure for imports and seed operations.
- PostgreSQL and SQL Server samples use the same declarative application model,
  Bean Validation, cursor responses, warm commands, job handlers, and tests.

## Preserved Boundaries

- HOT routes read Redis only. A miss does not trigger hidden SQL I/O.
- SOURCE routes are explicit, bounded, indexed, and time-limited SQL reads.
- Writes are accepted by Redis first; SQL durability is asynchronous and
  observable through receipts.
- Repository implementations, route metadata, and Spring adapters are generated
  at compile time without runtime reflection.
- Growing lists use projections and keyset windows rather than offset scans or
  full aggregate hydration.

## Consumer Version

```xml
<properties>
    <cachedb.version>0.8.0</cachedb.version>
</properties>
```

Use exactly one provider starter:

```xml
<dependency>
    <groupId>com.reactor.cachedb</groupId>
    <artifactId>cachedb-spring-boot-starter-postgres</artifactId>
</dependency>
```

or:

```xml
<dependency>
    <groupId>com.reactor.cachedb</groupId>
    <artifactId>cachedb-spring-boot-starter-mssql</artifactId>
</dependency>
```

## Compatibility

The public API change from `0.7.1` is additive. Existing compatibility
overloads remain available. Applications should nevertheless compile and run
their provider integration tests before deployment because route defaults and
cursor contracts are now more explicit.

## Distribution

- Maven packages: GitHub Packages under `com.reactor.cachedb`
- Release bundle: `cache-database-0.8.0-github-release.zip`
- Runnable examples: PostgreSQL and MSSQL sample repositories tagged `v0.8.0`

The release bundle includes binary, source, Javadoc, and POM artifacts for all
public modules, the BOM, documentation, and both sample projects.

## Validation

- Full Maven reactor: no failures or errors.
- PostgreSQL and SQL Server provider integration samples: no failures or errors.
- Public API compatibility, reflection-free framework rules, provider parity,
  sample architecture, documentation, Postman, package content, and whitespace
  gates: passed.

Framework release evidence is not an application cutover certificate. Each
consumer still needs representative warm coverage, data parity, memory sizing,
HA/failover, canary, and rollback evidence in its own staging environment.
