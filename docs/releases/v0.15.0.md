# CacheDB 0.15.0

## Scope

This release reduces serialization, Redis indexing and snapshot refresh overhead
and adds compile-time validated declarations. It does not turn CacheDB into an
automatic cache for arbitrary SQL, or change which system owns durable data.

| Area | Change | Application impact |
| --- | --- | --- |
| Entity/projection payloads | Direct length-prefixed encoding and cursor decoding | No temporary map on generated payload paths; unchanged Redis format |
| Generated metadata | Shared immutable column/index maps | Repeated metadata reads reuse the same maps |
| Redis reads/indexes | Batched access tracking and field-level index differences | One access batch; unchanged indexed values do not trigger index writes |
| Snapshot definitions | `scopedBy`, `scopedByString`, `withGeneratedJsonCodec`, `bind` | Less registration and conversion boilerplate |
| Snapshot reuse | SHA-256 while spooling; verified content reuse | Unchanged payloads are not reread/resubmitted; missing content triggers bounded retry |
| SQL write fences | Per-identity coalescing; conditional PostgreSQL UPSERT | Winning versions/delete tombstones remain in the business transaction |
| JDBC providers | Shared transaction/rollback/restoration boundary | COPY, SQL Server session settings and Oracle duplicate recovery remain provider-specific |
| Runtime roles | Automatic publisher-only executor for `CLIENT_ONLY` | No sample workaround or idle job/snapshot thread pools |
| Non-web workers | Explicit Spring Boot keep-alive in all sample worker profiles | Worker JVMs stay running without an HTTP listener |
| Declarative queries/jobs | `@CacheSeek`, method-level `@CacheJobHandler` | Validated keyset predicates and generated direct method calls |
| Snapshot reads/changes | Inclusive score ranges; bounded dirty-root claims | Filter before payload loading; coalesce changes without losing marks during a refresh |
| Administration | Separated consistency/write-behind inspectors | Bounded export budgets fail explicitly rather than collecting indefinitely |

## Upgrade

1. Align the BOM, provider starter, JSON module and processor to `0.15.0`.
2. Recompile generated bindings/codecs; do not hand-edit generated sources.
3. Retain the durable `cachedb_write_fence` table introduced in 0.14.0. Never
   clear it when replaying or removing business rows. No new business-table
   columns are required by this release.
4. Remove application-owned publisher-only executor workarounds if they merely
   duplicate the new auto-configuration. An explicitly supplied bean still wins.
5. Adopt new declarations per route; existing constructors, explicit codec APIs,
   handler interfaces and unbounded score-range pagination remain supported.
6. Recheck result membership/order, memory budgets, SQL durability, worker
   replacement and rollback on the application's own topology before cutover.

## Important Contracts

- Existing Redis values use adjacent `<keyLen>:<key><valueLen>:<value>` segments;
  `-1:` means null. The format is not an equals/semicolon-delimited protocol.
- Generated entities support at most 1024 persisted fields. Decoders reject
  malformed lengths, truncated fields and oversized payloads before parsing
  unbounded input. Unknown fields and repeated-field behavior are preserved.
- `@CacheSeek` accepts up to four sort-aligned LT/GT components and requires a
  unique ID tie-breaker. SQL values remain parameters, not string interpolation.
- Method job payloads require `@CacheJsonRecord` or an explicit typed
  `CacheValueCodec` bean. Legacy handler interfaces retain configured Jackson
  serialization; the new annotation does not silently fall back to Jackson.
- Generated JSON SPI providers are resolved once while constructing the plan,
  cached by value class and called directly thereafter. There is no hot-path
  field/method discovery. Spring itself is not claimed to be reflection-free.
- A range cursor is bound to its generation, partition revision and score bounds.
  Keep all of them unchanged on continuation; restart after a relevant refresh.
- Dirty roots are expiring hints, not a durable CDC log. Pending plus in-flight
  IDs share the `batch-rows` capacity. Overflow rejects the new marks explicitly.
  First publish a complete snapshot; retain an explicit scope and a durable
  change feed or periodic reconciliation for long outages.
- One-script job acceptance applies to standalone Redis or same-slot Cluster
  keys. Cross-slot queues use a pipeline plus checked enqueue/cleanup; that is
  not a cross-slot transaction or an exactly-once claim.
- Full job queues retain `CacheDistributedJobQueueFullException` and its existing
  `RuntimeException` base. Existing caller catch/HTTP retry behavior is not
  changed to an unrelated `IllegalStateException` hierarchy.
- Snapshot content reuse still reads the declared SQL sources. It avoids
  redundant payload loading/transmission, not source reconciliation.
- Write coalescing is limited to explicitly declared `LATEST_STATE` policies.
  `EXACT_SEQUENCE`, audit/trigger-driven writes and mixed-policy batches retain
  intermediate accepted writes and the locked seed/read/update fence path.
  PostgreSQL's single conditional UPSERT path applies only to coalescible batches.
- Admin exports are limited to 50,000 rows, 16 Mi UTF-16 characters of field
  content and 2,000 pages. Narrow filters when the explicit budget error occurs.

See the compiled scenarios in all three sample READMEs and
[typed snapshots and roles](../typed-snapshots-runtime-testing.md).

The public Maven repository and GitHub Packages promote the checksum-verified
release bundle instead of rebuilding its JARs. The SDK ZIP includes binary,
source and Javadoc JARs plus the parent/module/BOM POMs. Samples use the anonymous
public Maven repository; GitHub Packages remains an authenticated alternative.

Provider fixture validation is not Oracle RAC/Data Guard or SQL Server Always On
certification. Application-specific HA/failover evidence remains a deployment gate.
