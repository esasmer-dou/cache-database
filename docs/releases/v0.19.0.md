# CacheDB 0.19.0

[Türkçe](../../tr/docs/releases/v0.19.0.md) | [Upgrade guide](../upgrading-to-0.19.md)

**Release documentation: 0.19.0.** The [release page](https://github.com/esasmer-dou/cache-database/releases)
is authoritative for actual package availability and checksums. This document does not itself
assert publication, a release date or successful completion of release checks.

Raw COUNT/FACET T4 is **`PASS_BY_ACCEPTANCE_EXCEPTION`**, by the November 9, 2026 acceptance decision.
The numeric 2x throughput target (`rawT4target`) was **not achieved**. Historical numeric failures
remain unchanged; neither a measured 2x speedup nor technical impossibility is claimed.
Correctness, isolation, storage bounds and other performance/regression gates are not waived.
Other required 2x targets, including opt-in read coalescing, remain scoped acceptance criteria,
not blanket release results.

The November 10, 2026 (UTC) P-SDK candidate measured opt-in coalescing throughput at 2.2550x
with 64 callers and 2.9411x with 1,000 virtual-thread callers. The runner had 1 CPU and 4 GiB;
a separate Redis Pod was limited to 500 millicores and 384 MiB. Single-caller throughput was
0.8614x, so coalescing remains disabled by default. These measurements belong only to that
candidate, artifact, topology and workload; they do not establish final-artifact or universal speedup.
Async window latency is not per-request latency; tracking throughput/latency is report-only.
Review the [release checklist](../release-checklist.md) and
[artifact-specific performance evidence](../performance-benchmarks.md) before adoption.

## Release Evidence Authority

The authority for release checks is CI for the exact release commit and the evidence bound to
its source, SDK and sample artifacts. Check source/artifact hashes, declared scopes, native exits
and original reports together. Documentation, a successful compile or historical candidate totals
cannot substitute for that evidence. Missing or skipped required evidence is not PASS.
Original failures remain part of the record; later scoped evidence does not rewrite them.

`FrameworkPackage != universalGA`. Real-application routes, SQL durability, protection onboarding,
restore/replay and production cutover require application-specific evidence. A single-Pod Redis
process failover check does not certify physical-node HA, zero downtime, capacity, Oracle Data Guard
or SQL Server Always On. Those topologies must be qualified independently.

## Breaking Platform Requirement

0.19.0 requires **Java 21+ (LTS)** for the runtime, library bytecode and annotation processing;
building from source requires Maven 3.9+. Java 17 applications must remain on 0.18.x until they
upgrade their build, container and runtime. Running an older release's tests on JDK 21 did not
make that release require Java 21. Historical release requirements and artifacts remain unchanged.
Preview features are not required. See [virtual-thread readiness](../virtual-thread-readiness.md).

Keep the BOM, processor, provider starter, workers and optional CacheDB modules aligned at 0.19.0.
Before adoption, verify the complete matching artifact set and checksums on the release page.
A source version or example coordinate alone does not establish package publication.

## Compatibility And Opt-In Changes

New runtime configuration uses the immutable `CacheRuntimeOptions` builder, not extra components on
`CacheDatabaseConfig`. Existing public configuration/receipt/queue record shapes are retained.
Generated bindings must be recompiled on Java 21. This is not permission to mix incompatible
encrypted payloads, generation envelopes, index writers or projection workers in one keyspace.

Default Redis Function names are versioned side by side. Keep legacy libraries, names and markers
for legacy callers; custom names are not automatically isolated. Never use FUNCTION FLUSH, replace
a different body under an unchanged version, or reset counters to make an upgrade start.
Follow the [Function migration contract](../redis-functions-upgrade.md).

Spring Data complete-result selection uses `EntityRepository.entityQueryCapacity()`:
UNKNOWN is not unrestricted, and FINITE(0) is an active prohibition on entity queries.
Derived deletes select at most min(capacity, 10,001); an exactly full selection fails before any
mutation. Unpaged results similarly fail at their cap and advise Pageable/Limit rather than returning
an incomplete list. All selected IDs/tenants are validated before bounded bulk acceptance; no
delete-while-paging or per-ID ownership SQL bootstrap is introduced. Bulk failure can still report
partial Redis acceptance; it is not an atomic transaction or SQL-commit receipt.

## Security And Consistency Limits

- New plain atomic-batch receipts bind logical write intent independently of adaptive cache
  policy. Replays preserve the original receipt, versions and TTLs without another enqueue.
  Old callers/receipts retain strict legacy matching; no unverifiable backfill is performed.
  Encrypted keyed intent remains unchanged. See [retry identity](../bounded-runtime-operations.md#retry-identity-in-019).
- Propagating tenant/causal/trace context does not establish permission or query completeness.
  Version-certified point/bulk reads remain distinct from queries, pages, aggregates and projections;
  unsupported causal non-point reads fail rather than returning uncertified data.
- Encrypted fields have authenticated envelopes, explicit keys and bounded storage. There is no
  plaintext fallback or automatic legacy-plaintext migration. Blind indexes support only approved
  equality operations and reveal equality patterns; encrypted range/order/source operations remain
  restricted. REDIS_ONLY leaves SQL plaintext; REDIS_AND_SOURCE requires a compatible source contract.
- Protection onboarding for existing data requires application-specific qualification. Configure no production
  purge/reopen endpoint until ownership/version inventory, original-generation producers, guarded
  SQL workers, read/fill closure and every declared store have a verified migration contract.
  Do not manufacture ownership markers, current-generation stamps or empty success receipts.
- EMPTY activation does not authorize arbitrary IDs or reuse previously purged identities.
  The registered standalone `POINT_NO_QUOTA` profile with canonical `Long` IDs supports an explicit
  administrative `reserveAndAdmitFreshRange` operation after exclusive-domain provisioning and
  activation. It prepares at most 128 new IDs atomically; it does not write entities or SQL rows.
  Normal writes still require an available version range; administrators replenish it separately
  through `refillVersionRange`. After EMPTY reopening, use a later, non-overlapping ID range in
  the new generation. Unknown IDs outside an admitted range still fail with `MIGRATION_REQUIRED`.
  Cluster, quotas and projection-dependent creation are outside this preparation profile.
  See [fresh identities and version refill](../tenant-protection-components.md#prepare-a-bounded-new-record-range)
  and the [reopening contract](../tenant-data-protection.md#explicit-empty-reopening).
- Purge covers one entity namespace and tenant, not every entity or external copy. Unknown owners,
  mixed legacy entries or missing participants remain closed/incomplete. Redis-only purge retains
  source rows and requires migration before reopening; even COMPLETE does not reopen admission.
- Retention covers the indexed resident set, not all cold SQL history. EVICT_CACHE is not source
  deletion; retention DELETE uses ordinary write-behind. Neither implies backup/log/export erasure.
- Redis acceptance, a future completing and a metric labelled hit are not SQL durability. Keep finite
  deadlines, reconcile uncertain writes, and never blindly retry an ambiguous mutation.

## Release And Rollout Gate

Release approval is determined by exact release-commit CI and artifact-bound evidence, not document
headings. It requires complete standalone/Cluster/provider tests, capability-qualified JFR evidence,
sample/API qualification, performance thresholds and security onboarding checks. Missing or skipped
required evidence is not PASS. Application HA, restore/replay and production cutover need their own
evidence even after framework acceptance.

Follow the [upgrade and rollback sequence](../upgrading-to-0.19.md). Keep both language versions,
the changelog, release history, package checksums and actual publication status consistent.
