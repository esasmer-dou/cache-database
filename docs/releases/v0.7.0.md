# v0.7.0

Release tag: `v0.7.0`

CacheDB `0.7.0` makes bounded Redis routes explicit from declaration through
warm-up, runtime reads, testing, and operational evidence. It preserves the
Redis-first, reflection-free design while reducing application code.

## Highlights

- `@CacheRepository` generates typed hot, source, warm, projection, command,
  keyset, generated-ID, and optimistic-write implementations.
- `HotWindow` reports route coverage and exposes complete results only when the
  requested active window is proven available.
- `updateHot` rejects unsafe partial merges when the current entity is absent
  from Redis instead of hiding a SQL round trip.
- `@CacheScheduledWarm` generates direct-call Spring tasks at compile time;
  runtime annotation reflection and `Method.invoke` are not used.
- PostgreSQL and SQL Server have explicit provider starters with fail-fast
  provider selection and provider identity telemetry.
- The test kit, Maven doctor plugin, OpenRewrite recipes, BOM, and optional admin
  starter are published as first-class artifacts.
- PostgreSQL and MSSQL samples expose matching bounded warm routes, Postman
  flows, and live provider integration tests.

## Consumer Version

```xml
<properties>
    <cachedb.version>0.7.0</cachedb.version>
</properties>
```

Import `cachedb-bom`, choose exactly one provider starter, and keep
`cachedb-annotations`, `cachedb-processor`, plugins, and test support on the
same version.

## Upgrade Notes

Hot routes no longer imply that any partially available Redis result is safe to
return as a complete page. Warm the exact route scope and inspect coverage.
Applications should map unavailable required coverage to an explicit service
response such as HTTP 503 instead of silently scanning SQL.

Optimistic partial updates require the current entity to be present in Redis.
Use a full command model or an explicit bounded source read when it is not.

Source and warm SQL remain bounded and validated. Keep archive, reporting, and
ad-hoc full-history reads on explicit SQL routes.

## Validation

- Clean 20-project reactor: 283 tests, no failures or errors, and 3 explicit
  topology-gated skips covered by dedicated infrastructure evidence lanes.
- PostgreSQL and MSSQL standalone samples: 8 unit tests plus 1 live provider
  integration test each.
- Public API, benchmark thresholds, provider parity, Postman, English/Turkish
  documentation, release artifacts, and framework-principle gates passed.
- The release bundle contains binary, source, javadoc, and POM artifacts for 16
  public modules plus the CacheDB BOM.

## Production Boundary

CacheDB does not turn an arbitrary SQL workload into a safe Redis workload.
Every production route still needs an explicit active-data policy, projection
contract, memory budget, warm/reconciliation plan, source-route boundary,
observability, rollback plan, and application-specific topology evidence.
