# CacheDB 0.18.0

Post-release hardening is tracked in [0.18.1](v0.18.1.md), not by replacing this
published tag or its packages. It adds composite-signature fallback, causal
Cluster/task propagation, refresh lifecycle and regrouping diagnostics. Source
layout and the full-environment anti-skip gate are also aligned. Tenant aggregate
and facet Lua optimization is **Deferred to 0.19.0**.

[Türkçe](../../tr/docs/releases/v0.18.0.md)

This release adds bulk L1 reads, bounded soft-TTL refresh, causal entity
read tokens, scan-resistant L1 eviction, indexed scalar aggregation, declarative
facets, composite exact indexes and tenant-aware atomic batches, partition windows
and projection reads. Independent JDBC mixed-write compaction requires explicit
schema opt-in; different IDs alone do not prove that operations commute.

See [configuration, examples and limits](../near-cache-facets-indexes.md).

## Compatibility and Rollout

- Java 17 library bytecode and Java 21 build/sample compatibility are retained.
- Existing NearCachePolicy constructors and AggregateResult constructors/accessors
  remain available. Soft TTL defaults to zero; existing entity payload frames do not change.
- AggregateResult adds decimalAverage. Applications with a strict JSON response
  schema should map transport fields explicitly rather than exposing framework records directly.
- Legacy entity APIs retain their typed tenant exceptions. The new facet and
  tenant batch/partition/projection surfaces reject scope violations with IllegalStateException.
- Bulk reads preserve caller order and duplicates; only Redis fetch identities are deduplicated.
- Regenerate bindings and align processor, BOM, starters, clients and workers.
- Deploy all writers and rebuild indexes before selecting newly declared composite indexes.
- Composite indexes retain the existing index maintenance/degraded-index recovery
  contract; payload publication and every index key are not one atomic query snapshot.
- Tenant markers remain immutable. Causal tokens certify minimum entity Redis versions,
  not SQL durability or projection freshness. Hard limits fail rather than truncate.
- Source changes are not evidence of publication, full production capacity or
  application-specific Always On/RAC/Data Guard certification.

## Verification

The final runtime sources passed acceptance in an isolated Kubernetes namespace.
No build, test or runtime probe was executed on the developer workstation.

| Check | Result |
| --- | --- |
| Full 23-module reactor | 730 test records: 728 executed, 2 topology-dependent skips; 0 failures/errors |
| PostgreSQL, SQL Server and Oracle samples | 26 tests each; 0 failures/errors/skips; fresh SQL database/schema and Redis test state |
| Public API and generated repositories | Existing baseline retained; compile-time facet/composite/soft-TTL validation passed |
| Packaged Jackson-free codec/snapshot path | 1,260/1,260 cold and repeated measurements below 50 ms; maximum 31.05 ms |
| Legacy compatibility | 60 functional measurements passed; 7 reached/exceeded 50 ms, maximum 385 ms; reported separately |
| Package contents | 19 public modules with binary/source/Javadoc JARs: 57 JARs; 21 POMs in the staged Maven repository |
| Standalone package consumption | All three samples built without framework sources; CacheDB artifacts were removed from the consumer cache before each build |
| Repository checks | README links/quality, Turkish text, Postman contracts, provider parity, framework principles and benchmark thresholds passed |

The strict latency gate includes scenario first-use work, but not JVM launch or
compilation. It is not an HTTP, SQL, WAN or production-capacity SLA. The workspace
was limited to 2 CPUs and 4 GiB. Standalone Redis and a six-node Redis Cluster were
used with live provider fixtures; this does not certify a production HA topology.

The skipped tests were MssqlListenerFailoverSqlServerTest and
OracleServiceNameFailoverIntegrationTest: their real listener/service-name failover
topologies were not available. No application-specific Always On, RAC or Data Guard
certification is claimed.

Pre-publication consumer resolution used a separate staged file-based Maven
repository. Distribution reuses these tested JARs without rebuilding them.
