# CacheDB 0.17.0

[Türkçe](../../tr/docs/releases/v0.17.0.md)

## Read and Write Changes

| Capability | Contract |
| --- | --- |
| PATCH batching | Consecutive matching SQL shapes use JDBC batches on PostgreSQL, SQL Server and Oracle. Mixed groups retain causal order and the provider's UPSERT/DELETE batching. |
| PATCH coalescing | Unversioned adjacent changes can merge fields; later assignments win. Versioned PATCH predecessors are never discarded. Normal generated entities retain their version fence. |
| Redis predicates | AND resolution stops on empty candidates; small sets use membership probes. Common-slot exact intersections execute server-side. IN keys are deduplicated and fetched in bounded batches. |
| L1 eviction | Segments use access order rather than insertion order. Generated deeply immutable records can reuse a decoded instance; mutable entities retain defensive decoding. |
| Numeric deltas | `@CacheDelta` adds a bounded numeric change to a hot entity through optimistic atomic Redis acceptance. Integer/decimal calculations do not use Lua floating-point arithmetic. |
| Aggregates | `@CacheAggregate`, derived `countBy...`, `count` and `aggregate` operate on the bounded active set. Covered predicates/fields avoid entity payload reads; decimal sums use exact indexed values, not ZSET double scores. |
| Ordered payload reads | Supported common-slot sort/page windows fetch index membership and payloads in one server call. Unsupported topology/shapes fall back; access bookkeeping can still make separate Redis calls. |
| Tenant scopes | `@CacheTenantId` and `CacheTenantContext` scope queries and guard reads/writes. Ownership is checked again at the atomic write boundary. |
| Local watchers | `registerWatcher` and generated `@CacheWatcher` Spring adapters report predicate transitions after local repository acceptance. Dispatch is bounded and best-effort. |
| Schema evolution | `@CacheSchemaVersion` and `CachePayloadUpcaster` let new readers consume older payload bodies without flushing Redis. Unknown future versions fail closed. |
| Compression | Optional UTF-8 byte thresholds use JDK fast DEFLATE and Base64 framing only when beneficial. Decoding remains enabled after compression is disabled. |

See [configuration and examples](../hot-path-controls.md).

## Resource and Consistency Limits

- The Java 17 library contract remains; the build/test JDK and runnable samples use Java 21.
- Numeric deltas require a complete hot row. They reuse the configured bounded PATCH retry budget; contention can return an optimistic conflict. They are not SQL arithmetic, a distributed lock, or a wallet transaction guarantee.
- Aggregates cover Redis's active set, not all SQL history. Candidate budgets apply. Dynamic hot policies and non-covered predicates/fields may require bounded payload decoding. These reads are not a transactionally consistent multi-key snapshot.
- Common-slot IN fetching bounds the **total materialized memberships**, including duplicates across sets. Cross-slot fetching uses a cardinality phase followed by pipelined guarded reads; it is not one RTT across the cluster.
- Single-call ordered fetching has a 1,000-result limit, 10,000 scan/offset bounds and a 16 MiB reply budget. Cached LIST pages remain all-or-nothing when rows expire or are deleted.
- L1 sharing excludes schema-upcast/compressed paths and relations. TTL, invalidation, entry and byte-reservation budgets remain. L1 is not linearizable.
- Tenant enforcement needs an application-authenticated scope. Missing context is denied for tenant entities. Trusted maintenance must explicitly open `CacheTenantContext.administrative()`; do not accept this privilege or tenant IDs directly from untrusted headers. Ownership bootstrap needs a trusted by-ID SQL loader. Owner metadata survives eviction/deletion and must be included in memory planning.
- Tenant mutation through atomic multi-entity batches, generic unscoped partition windows and inherited unscoped projection contracts is rejected rather than bypassing isolation. Use explicit scoped repositories/contracts.
- Watchers observe local repository mutations, not all pods, SQL writers, warm imports or atomic-batch envelopes. They are not a durable CDC/fraud/payment event mechanism. At most 64 watchers per repository, four JVM-wide dispatch partitions, 256 queued tasks and 4 MiB queued-byte reservation per partition are allowed. Oversized events are dropped and logged; callbacks must be short/nonblocking. `droppedWatcherNotifications()` exposes budget drops.
- The default compression threshold is zero. Maximum decoded output is 16 MiB; the underlying codec's own stricter limits still apply. Framing prefixes `~v` and `~Z:` are reserved. Compression ratio is data-dependent, not a promised 60–85% saving. `SnapshotPlan.withSpoolCompression(bytes)` separately compresses temporary disk blocks while preserving published JSON and logical publication budgets.

## Upgrade Order

1. Align BOM, processor, starters, readers and workers at `0.17.0`; regenerate bindings.
2. Keep new payload framing disabled until every consumer understands it. Drain old workers before producing new operation/framing forms. Keep durable write-fence tables and Redis versions.
3. Plan schema evolution as an expand/contract rollout. New readers can upcast old data; old readers cannot automatically understand renamed fields, compressed frames or a future schema. Upcasting does not migrate SQL DDL and does not automatically rewrite Redis on read.
4. Declare the hot set, warm it, then verify data/order parity, tenant isolation, memory and error behavior before switching traffic.
5. Run the full provider, Cluster, compatibility and latency lanes on the exact release sources. Repository changes alone are not publication or application-specific HA certification.
